### Nav2 vs SLAM

- **Nav2(Navigation2)**
	- ROS 2 자율주행 패키지. 켜기만 해서는 안 되고 **파라미터 튜닝 필수**
	- Cartographer는 센서 신뢰도 위주 파라미터, Nav2는 **최저/최대 이동 속도·회전 속도** 등 주행 파라미터 영향이 큼
	- SLAM으로 만든 **지도가 반드시 필요** (지도는 최대한 깨끗하게)

| 구분 | SLAM | Nav2 |
| --- | --- | --- |
| 목적 | 지도 생성 + 위치 추정 동시 | 주어진 지도 위에서 목표까지 자율주행 |
| 지도 | 실시간 생성 | 저장된 맵(`.yaml`/`.pgm`) 로드 |
| 위치 보정 | SLAM 노드 | **AMCL** |
| 명령 방식 | teleop/조이스틱 | RViz `2D Pose Estimate` → `Nav2 Goal` 클릭 |
| Costmap | 1개 | 2개 (global/local) → 연산량 약 2배 |

- **TF 구조는 동일**: `map → odom → base_footprint`
	- `map → odom` 발행 주체만 다름 (SLAM 노드 vs AMCL)
	- `base_link`가 아니라 `base_footprint` 사용
	- 입력도 동일: odometry, `/scan`, (IMU, 카메라)
- **초기 위치**
	- 로봇 실행 시 위치는 항상 `(0, 0)`, 맵 원점은 **매핑을 시작한 위치** (이미지 꼭짓점 아님) → 둘이 다름
	- Nav2 실행 직후엔 로봇 위치가 안 나옴 → RViz에서 `2D Pose Estimate`로 직접 지정
	- 사람이 찍은 위치는 대략값 → AMCL이 계속 보정 ⭐
- **새로 등장하는 토픽**
	- `path`: 전역 경로 / trajectory: 경로 + 소요 시간·속도 변화 포함
	- `cmd_vel`(Twist): 선속도·각속도. 위치만으로는 주행 불가, 속도 필요
	- 자율주행은 기본적으로 **후진 없음** 전제 (파라미터로 허용 가능)

### Nav2 스택 구조

| 계층 | 역할 | 알고리즘 |
| --- | --- | --- |
| Planner server | **전역 경로**: 현재 위치→목적지. 맵에 있는 장애물만 회피 | A*, Dijkstra (Hybrid A*) |
| Controller server | **지역 제어**: 전역 경로 따라가며 동적 장애물 회피, `cmd_vel` 출력 | DWB, MPPI, RPP, Graceful |
| Recovery(Behavior) server | 충돌·동작 불가 시 복구 (후진·회전·대기) | — |

- 전역 경로만 있으면 동적 장애물 앞에서 **사라질 때까지 정지** → Controller 필요
- 전역 경로 = 웨이포인트, Controller = 웨이포인트 사이 이동 담당
- Recovery 예: 정면 충돌 시 제자리 회전 불가 → 후진. 장애물이 라이다 **최소 스캔 범위 안**에 들어와도 후진 (재스캔 위해)
- 전역 경로 계산 시간은 중요하지 않음 (A* vs Dijkstra 체감 차이 0.x초) → **중요한 건 지역 제어**

### AMCL (Adaptive Monte Carlo Localization)

- **원리**: 알려진 2D 지도 위에서 로봇의 위치·방향을 파티클 필터로 추정
	1. odometry로 위치 예측 → 후보(파티클, RViz 초록색) 다수 생성
	2. 각 후보 위치에서 라이다 스캔이 **맵과 일치하는지** 점수 비교
	3. 가장 적합한 후보로 위치(TF) 보정
	- 주행 내내 **주기적으로 반복** (odom 오차는 계속 쌓이므로)
	- 라이다(또는 라이다처럼 만든 카메라) 없으면 불가
	- 초기 위치 오차가 너무 크면 보정 못 함 ⭐

| 조정 대상 | 올리면 | 내리면 |
| --- | --- | --- |
| 라이다 사용 반경 | 비교 대상↑, 정확↑ | 연산량↓ |
| 맵 해상도 | 정확↑ | 속도↑ |
| 파티클 수 | 후보↑, 정확↑ | 연산량↓ |

- **주요 파라미터**
	- `robot_model_type`: 차동 구동 → Differential / 옴니휠 → Omni
	- `tf_broadcast: true` 유지 (단, 다른 노드의 map↔odom broadcast와 **중복 금지**)
	- `scan_topic`: 사용할 라이다 선택
	- `min_particles` / `max_particles`: 가설 개수
	- `alpha1`~`alpha5`: 회전·선형 이동 노이즈. **추천값 없음** — 바퀴 위치, 4륜/6륜, 모터 수에 따라 다름 → ROBOTIS TurtleBot 기본값에서 실험으로 조정 ⭐
	- 레이저 모델 오차 폭 (`sigma_hit: 0.2` m): 맵 파일도 오차가 있다고 전제. **A 로봇으로 매핑, B 로봇으로 주행**하면 라이다 값이 달라지므로 중요 (프로젝트 3: 맵 1개에 TurtleBot 4대 이상 주행)
	- `z_hit`, `z_rand` 등 관측 혼합 가중치: 보통 수정 안 함
	- `update_min_d`, `update_min_a`: 갱신 주기 / `max_beams`: 평가 빔 수
- **AMCL + SLAM 동시 실행 금지 (기본 설정)** ⭐
	- 같은 TF·odometry·센서를 공유 → 둘 다 로봇 위치를 TF에 publish → 좌표가 두 값 사이를 왔다 갔다 함
	- 리매핑으로 odom을 2개로 나누면 가능

### Costmap과 인플레이션

- **Costmap**: 지도 위 위험 구간에 비용 부여. 층 = Static / Obstacle / Inflation
- **인플레이션**: 장애물을 로봇 반경만큼 부풀려 로봇을 **점으로 취급** 가능하게 함 + 감쇠 벌점으로 경로가 복도 가운데로 흐름

```
비용(d) = 254 (치명)        , d < r          # 들어가면 충돌 확정
        = e^(-k (d - r))   , 그 밖          # 가까울수록 벌점
d: 장애물까지 거리, r: 로봇 반경, k: cost_scaling_factor
```

| 파라미터                  | 크게                            | 작게                 |
| --------------------- | ----------------------------- | ------------------ |
| `inflation_radius`    | 안전↑, 좁은 문이 막힌 것처럼 보여 경로 생성 실패 | 벽에 붙어 감, 너무 작으면 충돌 |
| `cost_scaling_factor` | 벌점 빨리 사라짐 → 대담한 주행            | 벌점 넓게 퍼짐 → 소심한 주행  |

- **로봇 반경은 외접원 반지름** ⭐ — 사각형 한 변의 절반이 아님

```
예) 로봇 400 × 400 mm
대각선 = sqrt(400² + 400²) ≈ 566 mm
robot_radius ≈ 283 mm   (200 mm 아님)
```

- **Local Costmap 파라미터**

| 파라미터 | 의미 / trade-off |
| --- | --- |
| `robot_radius` | 로봇 반경 (외접원) |
| `resolution` | 해상도 |
| `width` / `height` | 지역 costmap 크기. 클수록 멀리 보지만 부하↑ |
| `inflation_radius` | 장애물 부풀림 크기 |
| `obstacle_max_range` | 장애물 측정 최대 거리 |
| raytrace(clearing) 범위 | 빈 공간을 지우는 범위 |
| smoother | 각진 경로 → 곡선. 부드러울수록 부하↑ |

### 전역 경로 — Dijkstra vs A*

```
Dijkstra: 우선순위 = g(n)                 # 출발점부터 누적 비용
A*:       우선순위 = f(n) = g(n) + h(n)   # h: 목표까지 추정 비용(휴리스틱)
```

| 구분 | Dijkstra | A* |
| --- | --- | --- |
| 탐색 | 모든 방향 균등 확장 | 목표 방향 우선 확장 → 탐색 셀 적음 |
| 유리한 맵 | 장애물 적고 단순 (직진·좌회전 정도) | 복잡, 후보 많음 (교차로 수백~수천) |

- A*가 **항상 빠르거나 항상 짧은 건 아님** — 휴리스틱 조건에 따라 다름. 보편적 우열 없음, 맵·로봇에 맞게 선택
- 팀플: 미로 내 장애물 개수를 비교하며 선택

| Planner 파라미터 | 의미 |
| --- | --- |
| `use_astar` | `true` = A* (기본), `false` = Dijkstra |
| `allow_unknown` | 미탐색 구간을 갈 수 있는 공간으로 둘지 |
| `tolerance` | 목표가 막혔을 때 근처 대체 목표 탐색 범위 |

- 계산 시간 제한도 설정 가능 (예: 3초 내 못 구하면 미사용). 대부분은 기본값 유지
- 회전은 드리프트를 키우므로 최소화
- 옴니휠/메카넘: 중심축 고정 제자리 회전 가능. TurtleBot은 중심축이 변함

### 지역 Controller — DWB vs MPPI

- **약자**
	- DWB: **Dynamic Window approach** 기반 (ROS 1 DWA local planner의 후속)
	- MPPI: **Model Predictive Path Integral**
- 입력: 현재 위치·속도 + 주변 costmap → **다음 주기**의 속도 명령 계산
- 단위: ROS는 **rad, m** (도·km 안 씀)

| 구분 | DWB | MPPI |
| --- | --- | --- |
| 방식 | 속도 공간 `(v, ω)` 샘플링 → 짧은 미래 시뮬레이션 → 채점. 전면 바운더리에 장애물 들어오면 감속/정지 | 제어 시퀀스 샘플링 + 로봇 모델로 **미래 궤적 예측** → 비용 기반 최적 선택 |
| 전제 | **장애물이 먼저 비켜갈 것** | **로봇이 장애물을 피함** |
| 동적 장애물 기본 동작 | 없어질 때까지 정지 | 즉시 회피 (경로 계속 재수정) |
| 단점 | 바운더리 탐색 때문에 **S자로 흔들리며 주행** | 연산량 많음 (CPU 벡터화 연산, 샘플 수가 시간 결정) |
| 부하 | 4종 중 최소 | 큼 |
| 사용처 | 물류 창고, 서빙·배달 로봇 | 상황에 맞게 |

- 물류 창고에서 지게차가 아니라 사람이 먼저 피하는 것과 같은 개념 → DWB
- DWB도 파라미터·바운딩 박스 크기·갱신 주기를 바꿔 회피하게 만들 수 있음 (현업 방식)
- 선택 기준은 연산 성능이 아니라 **로봇의 목적** + **정해진 주기 안에 계산 가능한지** ⭐
- Jetson에서는 MPPI 사실상 어려움 — 비전·매니퓰레이터도 함께 돌려야 함 (튜닝 잘하면 사용 가능)

### 도착 판정 · 가감속 · 복구 + 튜닝 팁

- **도착 판정**
	- odom은 측정값이라 정확한 도착 불가 → `xy_goal_tolerance`, `yaw_goal_tolerance`
- **가감속 제한**
	- 토크를 0으로 끊지 말고 서서히 정지
	- 제약 강할수록 느려짐, 끄면 빠르지만 흔들림·위치 이탈
- 큰 경로 변화가 생기면 기존 전역 경로 **취소 후 새로 등록**하는 게 더 빠름

| 팁 | 내용 |
| --- | --- |
| 도착 허용 오차 | `15~20cm`, 각도 약 `40°`로 여유 있게 → 이동 빨라짐 |
| 도착 후 자세 | 바로 카메라 스캔 X → **카메라 기준으로 자세 한 번 더 정렬** |
| 가감속 | 최대 속도의 약 `15%` |
| 복구 | 후진 안 씀 → costmap에서 장애물을 **많이 부풀림**, 부풀린 영역에 들어가면 회전으로 탈출 |
| 라이다 | 매핑은 앞뒤 2개, 내비는 **앞 라이다만** (후진 안 하므로) |
| 쉬운 튜닝 대상 | costmap 크기, 로봇 속도, 샘플링 개수, 해상도 |

## 알게 된 것

- Nav2는 SLAM과 TF 구조가 같고 `map → odom`을 AMCL이 발행함 → **SLAM과 AMCL을 같이 켜면 TF 중복으로 위치가 튐** ⭐
- AMCL은 odom 후보(파티클)를 라이다-맵 매칭으로 걸러 위치를 보정함. 사람이 찍은 초기 위치도, odom도 그대로 믿지 않음
- 로봇 반경은 **외접원 반지름**으로 넣어야 함 (400×400mm → 약 283mm) ⭐
- A*(`f = g + h`)가 항상 Dijkstra보다 나은 건 아님 — 맵 복잡도에 따라 선택
- DWB는 장애물이 비키길 기다리는 방식이라 가볍고, MPPI는 미래 궤적을 예측해 회피해서 무거움 → **로봇 목적과 계산 주기**에 따라 선택
