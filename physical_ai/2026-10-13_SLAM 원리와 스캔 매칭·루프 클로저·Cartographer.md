## 오늘 배운 것

### SLAM 기본 개념

| 구분 | 역할 | 비고 |
| :--- | :--- | :--- |
| Localization | 알려진 지도에서 현재 위치 추정 | 센서 오차로 발생한 편차를 보정하여 위치 추정 |
| Mapping | 위치를 알고 있는 상태에서 관측을 지도에 누적 | 맵 값: 장애물 / 비장애물 / 미관측 |
| SLAM | 위치와 지도가 모두 불확실한 상태에서 둘을 함께 갱신 | 도면만 입력해서는 부족함 |
| Odometry | 연속적인 이동 추정 | 장기 오차 누적. SLAM은 지도와의 일관성을 다룸 (슬라이드 45) |

- 도면 맵과 로봇이 인식하는 맵은 불일치 발생
	- 원인: **센서 오차**, **오도메트리 드리프트**, **바퀴 슬립·헛돎**
	- 로봇이 "명령대로 움직였다"고 신뢰하면 안 됨 (`cmd_vel`로 10 m 전진 명령 → 실제 이동 ≠ 10 m)

### 센서 3종과 치명적 단점

| 센서 | 측정 | 치명적 단점 |
| :--- | :--- | :--- |
| LiDAR | 360° 거리 값 (장애물 위치) | 데이터 양 큼 |
| IMU | 자세·각도 | 자기장 영향(자석, 배터리, 모터 근처) 시 오차 |
| 엔코더 | 바퀴 회전량 | 슬립·헛돎 측정 불가 (기계적 회전량만 측정) |

- 세 센서를 융합하여 사용 (센서마다 측정 대상이 다름)

### 드리프트와 오도메트리

- 드리프트: 센서 값을 주기마다 누적해 이동량을 계산하므로 오차가 함께 누적되는 현상
- 오도메트리(odom) = **로봇의 실제 위치가 아니라 센서 융합으로 추정한 위치**
- ROS 토픽 이름: `odom`

| 구분            | 의미       | 토픽        |
| :------------ | :------- | :-------- |
| 초록 경로 (이상 경로) | 명령 값 누적  | `cmd_vel` |
| 빨강 경로 (추정 경로) | 센서 융합 추정 | `odom`    |

- 좌표계에 둘을 함께 그려 비교함. 겹치는 구간 / 벗어나는 구간 존재
- 실제 타입: `cmd_vel` = `geometry_msgs/Twist`(속도), `odom` = `nav_msgs/Odometry`(pose + twist 포함)로 서로 다름. 위치·속도 계열이라는 점만 유사

### 각속도의 오차

- 선속도(전·후진): 슬립이 없으면 오차 거의 없음
- 각속도(회전): 오차 가장 큼
	- 회전 시점에는 오차가 작아 보이지만 회전 후 직진 거리가 길수록 횡방향 오차 확대
	- 회전을 반복하면 오차가 계속 누적되어 복귀 시 위치가 크게 벗어남
- 강사 방식 (개인 경험): **각도는 IMU**, **각속도는 엔코더**(좌우 바퀴 속도 차이)로 추정. 소수점 8자리까지 사용 ⭐
- IMU + 엔코더 2개로도 부족함: IMU 오차 + 바퀴 헛돎이 동시에 발생하면 보정 불가 → LiDAR 필요

### 스캔 매칭 (Scan Matching) - 로컬라이제이션의 핵심

- LiDAR는 장애물 위치를 알려줌. 벽·기둥은 고정되어 있으므로 로봇이 10 cm 이동해도 벽 위치는 불변
- 연속 스캔의 **겹치는 부분이 일치하도록 로봇 위치(odom 추정값)를 보정**
	- 오도메트리가 틀어졌더라도 LiDAR 스캔 겹침 기준으로 추정값 자체를 수정
	- 근거: odom은 실제 위치가 아니라 추정값이므로 수정 가능
- 슬라이드 보충 (슬라이드 12~13)
	- 새 스캔을 조금씩 이동·회전시켜 지도와 비교하고 가장 잘 겹치는 자세를 선택. odom은 탐색 시작 근처 위치(초기값)를 제공
	- 후보 자세별 거리 잔차 제곱합이 최소인 pose 선택 (예: 잔차 0.10, 0.10, 0.10 → 0.03 / 잔차 0.00, 0.10, 0.30 → 0.10 → 앞 후보 선택)
	- 모양이 반복되는 복도는 특정 방향의 보정이 어려움
- scan matching vs loop closure가 고치는 오차
	- scan matching: 프레임 단위 정합 오차 보정. 정합이 좋아도 긴 경로에서는 작은 오차가 누적됨 (슬라이드 14)
	- loop closure: 같은 장소를 다시 본 제약으로 누적(전역) 오차 보정
- 2단계 보정 구조 ⭐
	1. 센서 융합(EKF)으로 물리적 드리프트 1차 감소
	2. 스캔 매칭으로 잔여 오차 2차 보정
- 내부 연산: 스캔 점을 점군(point cloud)으로 변환 → 행렬 연산으로 정합 (Level 1 모듈 3 좌표변환 과제와 연결. 실무에서는 제조사·라이브러리 제공)
- 로컬라이제이션 주기는 빠를수록 유리

**전제 조건과 한계** 

| 상황 | 결과 | 이유 |
| :--- | :--- | :--- |
| 최초 시점 | 매칭 대상 없음 | 이전 스캔 데이터 없음 → 같은 위치를 여러 번 이동하며 스캔 누적 필요 |
| 개활지 (장애물 없음) | 오차 증가 | 겹치는 특징 없음 |
| 로봇 속도가 스캔 주기·범위 대비 과다 | 매칭 불가, LiDAR 값 신뢰 불가 | 연속 스캔 간 겹침 없음 |
| 복도·물류센터 (반복 패턴) | 매칭 어려움 | 위치별 스캔 형태가 동일 (강사 경험: 100 m 복도) |
| 반복 정합 | 벽 선이 두꺼워짐 | 정합 오차 누적 |

- 로봇은 "비슷하다"를 "같다"로 판단하지 않음. 데이터를 여러 번 누적해야 신뢰 가능 (SLAM은 반복할수록 정확해짐)
- 지연·주기·지터 정합 필요 (LiDAR 주기와 로봇 이동 속도 관계)
- 강사 예시 수치: LiDAR 주기 30~60, 유효 범위 5~6 m → "초당 6 m 이상 이동 금지". 슬라이드에 해당 수치와 계산 근거 없음 (강사 경험 수치로 취급). TurtleBot3는 이 속도에 도달하지 않음

**스캔 매칭 파라미터**

- LiDAR 유효 범위(min/max)를 제한하여 신뢰 구간만 사용
- 스캔 매칭 반복 횟수 / 사용 개수
- 점수 임계값 (예: 1점 만점 중 0.9 이상만 사용)

### EKF (Extended Kalman Filter)

- 역할: 센서 노이즈 필터링 + 센서 융합
- 핵심: **대상의 물리적 운동 모델**을 내장 (자동차·비행기·선박 모델이 각각 다름)
- 예시 (물리적으로 불가능한 값 제거)
	- 한 스텝에서 10 m/s → 다음 스텝에서 10,000 m/s: 불가능 → 제거
	- 각도만 보면 0° → 90°는 가능/불가능 판단 불가. 각속도 값과 함께 보면 이동 가능 여부 판정 가능 → 센서 융합이 필요한 이유
- 필터링은 수십~수백 개 샘플을 기준으로 판단
- 센서 개수 ⭐
	- 강사 설명: 센서가 많을수록 측정 가능 정보 증가, 노이즈 처리 부담도 증가
	- 단일 센서 EKF도 가능 (인공위성 사례: IMU 1개, 3축 각도 + 3축 각속도 = 6개 값). 오차 모델을 알고 있으면 적용 가능
	- 이동체는 보통 2~3개 센서 사용
- EKF도 적분 기반이므로 드리프트 발생. 만능 아님
- 사용 분야: 모빌리티, 항공우주

### 맵 표현과 해상도(resolution) ⭐

- 2D: x, y, yaw(θ) / 3D: x, y, z, roll, pitch, yaw
- ROS 각도 단위는 **radian만 사용** (URDF, 계산 모두 동일). 도(°) 사용 시 직접 변환
- 위치 단위 m. resolution = 1 픽셀당 거리(m/pixel)
	- TurtleBot 기본값 `0.05` (1 px = 5 cm)
	- 값이 작을수록 해상도 높음 → 맵 이미지·토픽 용량 증가
	- 강사 경험: Jetson Nano에서 `0.01`까지 가능, 그 이하는 연산 불가
	- 실내 약 5 cm, 야외는 `0.1`~`0.5`처럼 크게 설정
- 해상도 기준은 용량만이 아님: **검출해야 하는 최소 장애물 크기보다 해상도 값이 작아야 함**
	- 예: 책상 다리 5 cm 검출 → 5 cm 미만 필요
	- 예: 1 m/px에서 30 cm 장애물 → 픽셀 내용 구분 불가, 스캔 매칭 불가
- 맵 값: 검정 = 장애물, 흰색 = 비장애물, **회색 = 미관측**
	- **정정**: 강의에서 "값이 0, 1 두 개"로 설명했으나 실제로는 미관측을 포함한 3상태
	- 셀 갱신 (슬라이드 10): 레이저가 지나간 셀은 빈 공간 증거, 반사 끝점 셀은 점유 증거를 누적. 관측하지 않은 셀은 미지로 유지
- 회색(미관측) 영역 문제: 넓은 맵 + 미세 해상도에서 미관측 영역을 통로로 인식 → 경로 계획이 잘못된 경로 선택
	- 대응: 여러 번 순회하여 회색 제거. 노이즈로 해소되지 않으면 맵 이미지를 수동 편집
- 용량 예시 (슬라이드 11): 20 m × 10 m, 셀 0.05 m → 400 × 200 = 80,000셀. 0.025 m로 바꾸면 800 × 400 = 320,000셀 (셀 크기를 절반으로 줄이면 셀 수 4배)
	- **정정**: 강의 중 "0.05 → 32만 셀"은 슬라이드 수치와 다름. 32만은 0.025 m 기준 값

### 루프 클로저 (Loop Closure) ⭐

- 로봇이 경로를 이동한 뒤 **시작점(또는 이전에 방문한 위치)으로 복귀**한 상황
- 동작: 복귀를 감지하면 시작점과 끝점을 자동 연결, 전체 경로를 최적화해 맵을 하나로 정합
	- "같은 위치" 판정 반경은 파라미터로 설정
	- 결과로 맵 기준 위치와 오도메트리 위치가 바뀔 수 있음
	- 절차 (슬라이드 15): 이전에 본 장소 후보 탐색 → 기하학적 검증 → 제약 추가 → 전체 경로 최적화 (map 기준 pose 변경)
- 필요한 이유: 오도메트리를 고정해도 시작점과 끝점이 이어지지 않는 경우 발생 (강의 예: 용인 CJ 물류센터 시뮬레이션 맵 vs 실측 맵 비교)
- 패턴이 긴 환경(긴 복도)일수록 중요. 짧은 환경은 비교 대상이 많아 영향 작음
- 한계 ⭐
	- 비슷한 복도·반복 벽을 같은 장소로 오인하면 잘못된 후보 생성 → 맵 겹침
	- 자동 연결 결과로 맵이 찌그러질 수 있음
	- 루프 클로저 후 원래 형태와 비교하여 정상 연결 여부 확인 필요

### SLAM 패키지 비교 ⭐

| 항목 | Cartographer | slam_toolbox | cuVSLAM (NVIDIA) |
| :--- | :--- | :--- | :--- |
| 주 센서 | 거리 센서(LiDAR), **선택 IMU** | 2D LaserScan, TF (IMU 미기재) | stereo / RGB-D, 선택 IMU |
| 차원 | 2D 또는 3D (3D는 속도 느림) | 2D | 3D 6DoF |
| 구조 | submap + pose graph | scan matching + pose graph | 시각 추적 + SLAM |
| 주 연산 | CPU 중심 | CPU 중심 | NVIDIA GPU (CUDA) |
| 이 수업 | 2D 실행 예제 (오늘) | 원리 비교만 | 3D 카메라 실행 예제 (10/14) |

- IMU 사용 여부가 Cartographer와 slam_toolbox의 가장 큰 차이 (강의 발언). 슬라이드상 Cartographer는 선택 IMU, slam_toolbox는 IMU 미기재
- 선택 기준 (슬라이드 25)
	- 2D LiDAR 평면 지도 → Cartographer
	- GPU + stereo 6DoF → cuVSLAM
	- 기존 2D 지속(lifelong) 지도 운영 → slam_toolbox 비교
	- 텍스처 없는 흰 벽 → 센서·동선 재검토 (카메라 대응점 부족)
	- 긴 반복 복도 → 추가 관측·루프 동선 (LiDAR도 모호할 수 있음)

- Cartographer 방식 ⭐
	- 짧은 구간 스캔으로 **서브맵** 생성
	- 현재 스캔 ↔ 서브맵 ↔ 전체 맵을 교차 검증하여 누적 오차 제거
	- 현재 스캔을 활성 submap에 맞추며 이동 추정, 완성된 submap 사이 제약을 최적화해 전역 오차 감소 (슬라이드 17)
	- 서브맵을 여러 개 유지하므로 CPU 부하 큼
- 구성 (TurtleBot3) ⭐
	- Raspberry Pi 4코어 CPU로는 Cartographer 연산 불가 (Jetson Nano는 가능)
	- Pi(SBC): LiDAR, 엔코더, IMU **원시 데이터 publish**만 수행
	- 노트북: subscribe 후 맵 생성, 경로 생성 처리
	- Pi는 `cmd_vel`만 수신
	- 단점: 네트워크 단절 시 매핑·자율주행 중단 → 모듈 9 Edge Computing에서 단일 컴퓨터 통합 구조 학습 예정
	- 네트워크가 안정적이면 Pi 과부하 거의 없음
- Cartographer 토픽
	- publish: 맵 토픽, 서브맵 토픽
	- subscribe: odom, scan(LiDAR), IMU, 엔코더 계열
- RViz는 계산 도구가 아니라 시각화 도구
- 환경 (OT 슬라이드 4): Ubuntu 24.04 amd64, ROS 2 Lyrical, Isaac Sim 6.1, Isaac ROS 5.0, RAM 32 GB / VRAM 16 GB 이상. ROS 배포판 ABI 혼용 금지

### TF 구조 ⭐ (가장 많이 혼동되는 부분)

```text
map → odom → base_footprint → base_link → (wheel, lidar, camera, 관절 ... )
```

| 프레임 | 의미 |
| :--- | :--- |
| `map` | 환경(맵) 기준 |
| `odom` | 추정 위치. `map`과 로봇 사이에 위치 |
| `base_footprint` | 바닥에 투영한 로봇 중심점 (`base_link` 원점에서 바퀴 높이만큼 아래) |
| `base_link` | 로봇 실제 원점 |

- `odom`이 로봇(`base_link`)보다 상위여야 하는 이유 ⭐
	- 로컬라이제이션 보정 값을 로봇 위치에 반영해야 하므로, 추정 프레임이 상위에 있어야 전달 가능
	- 순서가 바뀌면 매핑이 되지 않음
	- SLAM 사용 시 로봇 위치는 `base_link` 좌표가 아니라 **`odom` 추정 값을 신뢰**
	- `odom`과 실제 로봇의 차이가 작을수록 보정이 잘 된 상태 (강의 예: 0.2°, 0.001 수준 차이)
	- 차이가 크면 로봇 하드웨어·센서 문제
	- `odom`은 맵 상에서 계속 갱신됨. 재시작 시 0 초기화 여부는 설정에 따름 (마지막 값 저장도 가능)
- `base_footprint` 필요성: 2D SLAM에서는 z가 무의미해 영향 적음. 3D 사용 시 바닥 기준 높이가 중요
- TF 읽는 법: 화살표 반대 방향으로 읽음
- TF는 URDF가 정의하므로 직접 작성하지 않아도 됨. TurtleBot3의 `tf tree`로 확인 가능
- 슬라이드 8: `odom`은 연속적인 이동 추정이지만 장기 오차 누적, `map`은 전체 지도에 맞게 보정되어 위치가 바뀔 수 있음. `base_footprint`는 바닥 기준, `base_link`는 본체 기준
- TF 발행자 (슬라이드 28, OT 슬라이드 13)

| TF | Cartographer 실행 | cuVSLAM 실행 |
| :--- | :--- | :--- |
| `map → odom` | Cartographer | cuVSLAM |
| `odom → base_footprint` | Sim wheel odom | cuVSLAM |
| `base_footprint → base_link` | robot_state_publisher | robot_state_publisher |
| 카메라 고정 TF | rig 발행자 1개 | 같은 rig 발행자 |

- 같은 TF를 발행하는 노드는 1개여야 함. cuVSLAM 실행 시 Sim의 odom TF를 먼저 끄고, 다른 SLAM은 종료

## 알게 된 것

- 오도메트리 = 로봇 위치가 아니라 추정 위치 ⭐
- `cmd_vel`(명령 누적) ≠ `odom`(추정) ≠ 실제 위치. 셋을 구분해야 함
- 오차는 각속도에서 가장 크게 발생. 회전 후 직진 시 편차 확대 ⭐
- 스캔 매칭은 겹침 기반으로 odom 추정값을 보정함. 이전 스캔 누적이 있어야 동작 ⭐
- 반복 패턴(복도, 물류센터), 개활지에서는 스캔 매칭 한계 ⭐
- 루프 클로저는 시작점 복귀 시 맵 연결·전체 경로 최적화. 맵이 찌그러질 수 있어 결과 확인 필요
- EKF도 만능 아님 (적분 기반 드리프트 존재)
- Cartographer는 CPU 무거움 → SBC는 publish, 노트북이 연산하는 분리 구조 ⭐
- TF 순서: `map → odom → base_footprint → base_link`. `odom`이 `base_link` 아래에 있으면 매핑 불가 ⭐
- ROS는 각도 단위로 radian만 사용

## 과제 팁 (프로젝트 2 — 미로 매핑) ⭐

- 환경 특성: 강사가 스캔 매칭이 어렵도록 **의도적으로 유사해 보이는 미로**를 구성함. 매핑 전략을 직접 설계해야 함
- 가장 빠르게 적용 가능한 패키지는 Cartographer (cuVSLAM은 맵이 단조로워 과잉)
- 튜닝 대상 (모두 파라미터로 존재)

| 항목 | 팁 |
| :--- | :--- |
| LiDAR 범위 | 신뢰 가능한 min/max 범위로 제한. 복도형 구간은 범위를 넓혀 꺾이는 구간을 포함시키면 매칭 가능. 범위 증가 시 부하 증가 → **적정값 탐색이 과제 목표** |
| 로봇 속도 | 스캔 간 겹침이 유지되는 속도로 제한 (LiDAR 주기·범위 대비) |
| 주기·지연·지터 | LiDAR 주기와 맞춰 튜닝 |
| 스캔 매칭 점수 | 임계값(예: 0.9) 설정, 반복 횟수 확인 |
| resolution | 장애물 최소 크기보다 작게 설정. 과도하게 작으면 용량·연산 증가 (`0.05` 기본, `0.01`이 Jetson Nano 한계) |
| 루프 클로저 반경 | 같은 위치로 판정하는 반경 설정 |

- 매핑 방법
	- 한 번 지나가고 끝내지 말고 **같은 구간을 여러 번 순회**해 스캔 누적
	- 시작점으로 복귀해 루프 클로저가 적용되었는지 확인
	- 회색(미관측) 영역이 남지 않게 반복
	- 루프 클로저 후 맵이 찌그러지지 않았는지 원본 형태와 비교
- 검증 방법: RViz에서 LiDAR 스캔(빨간 점)이 맵 벽과 일치하는지 시각 확인
- 구성: SBC(Pi)는 센서 데이터 publish만, 노트북에서 Cartographer 실행. 네트워크 연결 안정성 확보
- 맵 저장: PGM 포맷. 파일 용량 과대 시 resolution 조정
- 이동 속도: TurtleBot3는 속도 성능이 낮아 속도 한계 문제는 거의 없음 (강사 언급)

### 슬라이드 기반 실습·제출 팁 ⭐

- 첫 실행 전 5개 검사 (OT 슬라이드 12)
	1. `/clock`이 움직이고 `use_sim_time`이 모두 true인가
	2. `/scan`, `/odom`, 좌우 영상, CameraInfo가 들어오는가
	3. `map`에서 카메라까지 TF가 이어지는가
	4. 좌우 영상 시각과 실제 baseline이 맞는가
	5. 직진·회전·정지 명령이 올바르게 반영되는가
- Cartographer 실행 순서 (슬라이드 29~31)

```bash
bash preflight.sh cartographer
ros2 topic hz /scan
ros2 topic echo /odom --once
ros2 run tf2_ros tf2_echo odom base_footprint
ros2 launch waffle_slam_course cartographer.launch.py
rviz2 --ros-args -p use_sim_time:=true   # Fixed Frame=map, Map=/map, LaserScan=/scan
```

	- 필요한 입력: `/clock`, `/scan`, `/odom`, `/joint_states`. scan의 `frame_id`에서 base까지 TF 연결 필요
	- 천천히 사각 경로로 주행 후 시작 장소 재방문. map–scan 겹침, 벽이 이중으로 보이는지, 루프 클로저 전후 비교
	- 수동 주행 명령은 작게 시작 (`/cmd_vel`, `linear.x: 0.1`), 관찰 후 0으로 정지. 다른 제어기와 동시에 명령 전송 금지
- 저장은 지도와 상태를 따로 (슬라이드 32~33)

```bash
ros2 run nav2_map_server map_saver_cli -f "$PWD/maps/waffle_2d" --ros-args -p use_sim_time:=true
ros2 service call /write_state cartographer_ros_msgs/srv/WriteState \
  "{filename: '$PWD/maps/waffle.pbstream', include_unfinished_submaps: true}"
```

	- 저장 지도 확인 3가지: 색(검정 점유 / 흰색 빈 공간 / 회색 미지), 방 폭·해상도가 실제 장면 크기와 일치하는지, OccupancyGrid와 SLAM 상태 파일 구분
- 비교 실험은 한 번에 한 설정만 변경하고 같은 경로로 재주행 (OT 슬라이드 14, 슬라이드 42)
	- 기록 항목: 주기, 추적 중단, 루프 전후 오차. 정상 조건은 기준 실행 3회
- 제출물 (OT 슬라이드 15): 모듈 ⑥ 기준. 프로젝트 2와 동일한지는 확인 필요
	- launch, Lua, 캘리브레이션, 소스 SHA 저장
	- 지도 파일, 화면, rosbag 또는 로그
	- `report.md`: 조건, 관찰, 해석, 실패 원인 (성공·실패 모두 포함)

### 실패 시 트러블슈팅 (강의 + 슬라이드 40~41 기반 정리) ⭐

| 증상 | 점검 항목 |
| :--- | :--- |

| GPU 노드 기동 실패 | `nvidia-smi`, CUDA 의존성 (드라이버/런타임) |
| 흰 벽에서 추적 끊김 (cuVSLAM) | 대응점 부족. 조명·속도·시야를 한 가지씩 바꿔 원인 분리 |
