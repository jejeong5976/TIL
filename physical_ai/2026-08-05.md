# 🗓️ TIL: Git 실습 (SpartaPA repo)

## 시도한 것들 (진행 과정)

[SpartaPA](https://github.com/SpartaPA) repo에 협업자로 초대받아, 로컬 개발 환경 세팅부터 브랜치 작업, main 병합까지 Git 기본 협업 사이클을 처음부터 직접 수행해봄.

1. **VS Code 세팅**
   - Git 협업을 위한 VS Code 환경 구성 (터미널, Git 확장 등)

2. **레포 클론 및 브랜치 생성**
   - SpartaPA repo를 로컬로 clone
   - 내 이름을 딴 `joeun-jeong` 브랜치 생성 후 이동
   ```bash
   git switch -c joeun-jeong
   ```

3. **작업 → staging → commit → push**
   -  `joeun-jeong` 브랜치에서 코드 작업
   -  git add로 변경 사항을 스테이징
	   - `git add test.py`
   -  git commit 으로 스냅샷 기록
	   -   `git commit -m "test commit"`
   -  `git push origin joeun-jeong`으로 원격에 반영

2. **main branch로 병합**
   -  브랜치 작업 내용이 main에 합치는 과정 확인 
   → main과 팀원 브랜치가 `test.py`의 같은 코드를 다르게 수정한 상태로 병합을 시도해 conflict가 발생하는 것을 확인함.

5. **conflict 개념 학습**
   -  merge/rebase 시 같은 파일의 같은 부분을 다르게 수정하면 발생하는 conflict의 원리를 학습

## 알게 된 것

-  **브랜치의 개념**
	- 브랜치는 특정 커밋을 가리키는 가벼운 포인터일 뿐이라, 새로 브랜치를 파서 작업해도 main에는 영향이 없다는 것을 실습으로 확인
	-  version, 기능과 같은 부분을 branch로 나눠 관리하기도 함
	
-  **작업 흐름**
	- 작업 디렉터리 (코드 수정) → staging (`add`, 커밋할 변경 선택) → 커밋 (`commit`, 스냅샷 기록) → 원격 저장소 (`push`, 팀과 공유) 순서

-  **conflict**
	- 같은 파일의 같은 부분을 여러 사람이 다르게 고쳤을 때 Git이 어느 쪽이 맞는지 판단할 수 없어 사람에게 선택을 넘기는 것. `<<<<<<<`, `=======`, `>>>>>>>` 표식으로 양쪽 버전이 표시되며, 직접 최종 코드를 작성한 뒤 `add` → `commit`(또는 `rebase --continue`)으로 마무리한다는 원리를 배움.
	
-  **협업 시 브랜치를 나누는 이유** 
	- 여러 명이 동시에 같은 파일을 건드려도 각자의 브랜치에서 독립적으로 작업하면 서로의 작업을 건드리지 않고 코드 작성 가능
	-  작성 후 괜찮은 코드에 대해 branch로 merge함으로써 프로젝트를 효율적으로 관리 가능
